What Kafka is, and the parts it is made of

Apache Kafka is a distributed event log. Applications write events into it, Kafka stores them durably across several servers, and any number of other applications read them, each at its own pace. It sits in the middle of a system so that the apps producing data and the apps using it never have to connect to each other directly.

The problem it solves

A security team has web servers, firewalls and VPN gateways producing logs, and an alerting system, an HDFS archive and a dashboard that need them. Connected directly, that is 3 × 3 = 9 separate pipelines, each with its own format, retries and failure handling. Add one new source and you build three more.

With Kafka in the middle, each source writes once and each consumer reads once: 3 + 3 = 6 connections. A new consumer simply starts reading, even from data written last week, without anyone changing the producers.

What makes it different from a queue

In a classic message queue (or a Flume channel), a message disappears once it is delivered. Kafka keeps every event for a configured retention period, 7 days by default, whether or not anyone has read it. Reading only moves the reader's bookmark. That one design choice is what allows replay, many independent readers, and recovery after a consumer crashes.

The vocabulary

Event (record)
One fact that happened, such as "login failed on web01". It has an optional key, a value and a timestamp.
Topic
A named stream of related events, like a table name for data in motion: security-events, payments.
Partition
A topic is split into partitions, and each is an ordered, append-only log. Partitions let a topic spread across brokers and be read in parallel. See it in section 1
Offset
An event's position number within its partition: 0, 1, 2 and so on. It never changes, and it is how readers keep their place.
Producer
Any application that writes events to a topic. The key it chooses decides which partition each event goes to.
Consumer
Any application that reads events, starting from an offset and moving forward.
Consumer group
Consumers sharing one name split a topic's partitions between them, so each event is handled once per group. Different groups each get everything. See it in section 2
Broker
One Kafka server. It stores partitions on its disk and handles reads and writes for them.
Cluster
Several brokers working together, so data survives a server failure and load is shared.
Replica, leader, follower
Each partition is copied to several brokers. The leader copy takes all writes; followers copy it. Fully caught-up copies form the ISR. See it in section 3
Controller
The part of the cluster that manages metadata: it notices dead brokers and chooses new partition leaders. See it in section 4
Retention
How long events are kept, by time (log.retention.hours=168, 7 days) or by size. Old data is deleted whole files at a time, not per read.

How one event travels

  1. The producer hashes the event's key to pick a partition.
  2. It sends the event to the broker that leads that partition.
  3. The leader appends it to the end of the partition log, giving it the next offset.
  4. Follower brokers copy it. With acks=all, the producer is told "stored" only once every in-sync copy has it.
  5. Consumers fetch from their last offset, process the event, and commit their new offset.
  6. When retention expires, the old log file containing it is deleted.

Consumer groups and lag

Consumers in one group split the partitions between them, so each event is processed once per group. A consumer reads by moving its committed offset forward. Lag is how far that bookmark is behind the end of the log. A second application in a different group gets its own bookmarks and reads everything again.

Replication, leaders and acks=all

Each partition is copied to several brokers. One copy is the leader and takes all writes. The others are followers that copy the leader. Followers that are fully caught up form the in-sync replica set (ISR). If a leader's broker dies, an in-sync follower takes over, and no acknowledged event is lost.

    Who keeps the cluster's own records?

    Someone must remember which brokers are alive, which topics exist and who leads each partition. That is cluster metadata, and it is managed by one controller. For years Kafka stored it in a separate system, ZooKeeper. With KRaft (Kafka + Raft), Kafka stores it in its own replicated log, and Kafka 4.0 removed ZooKeeper entirely.

    Time is compressed for the classroom. The comparison is the point: with ZooKeeper, recovery grows with the amount of metadata; with KRaft, it does not.

    What to notice. On the ZooKeeper side, the new controller starts with nothing and must read every partition's record back from a different system before it can act, and because the controller was also a broker, its partitions are leaderless until then. Raise the partition count and the gap widens. On the KRaft side, every standby controller has been following the metadata log all along, so the takeover is a quick vote, and failing a controller does not take any of your data offline.

    Apache Flume: collecting logs and moving them in

    Kafka stores and serves events, but something has to collect them from the servers that write log files. Apache Flume is a collector from the Hadoop ecosystem built for exactly that: you describe a pipeline in a config file, start an agent, and it moves log lines into HDFS, Kafka or another destination, with no code.

    An agent is three parts in one JVM process

    Every Flume agent has a source that reads input, a channel that buffers events, and a sink that writes them out. Data moves in transactions: the source commits a batch into the channel, and the sink removes events from the channel only after it has written them. That handshake is what makes Flume reliable, as long as the channel itself survives.

    Sources
    exec (runs tail -F), TAILDIR (tails files and remembers its position), spooldir, syslog, netcat, kafka
    Channels
    memory (fast, lost on crash), file (write-ahead log on disk), kafka (Kafka holds the buffer)
    Sinks
    hdfs, kafka, hbase, logger, avro (to chain agents together)

    Every line is agent.component.name.setting. The agent name must match -n a1 when you start it, and a typo is silently ignored. Note that the source says channels (it can feed several) while the sink says channel (it reads exactly one).

    Changing the source or channel resets the run. The sink is deliberately slower than the source, as HDFS writes are, so a backlog builds up in the channel.

    memory + exec: everything in the channel, plus every line not read yet, is lost.
    file + exec: the channel's backlog survives on disk and is delivered after the restart, but tail -F restarts at the end of the file, so unread lines are still lost.
    file + TAILDIR: the source resumes from its saved position. Nothing is lost; a few lines may arrive twice. That is at-least-once delivery.
    Bonus: crash it, write 40 more lines while it is down, then restart with each source.

    The HDFS sink and the small-files trap

    The HDFS sink starts a new file whenever any of three limits is hit: hdfs.rollCount (default 10 events), hdfs.rollSize (default 1 KB) and hdfs.rollInterval (default 30 seconds). With the defaults, a busy agent creates a file every few events. The NameNode keeps every file and block in memory, roughly 150 bytes each, so millions of tiny files slow the whole cluster down.

    The lab sets rollSize to 128 MB (one block), rollCount = 0 (off) and rollInterval = 60 as a backstop so a quiet source still closes its file.
