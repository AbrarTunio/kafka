What Kafka is, and the parts it is made of

Apache Kafka is a distributed event log. Applications write events into it, Kafka stores them durably across several servers, and any number of other applications read them, each at its own pace. It sits in the middle of a system so that the apps producing data and the apps using it never have to connect to each other directly.

The problem it solves

A security team has web servers, firewalls and VPN gateways producing logs, and an alerting system, an HDFS archive and a dashboard that need them. Connected directly, that is 3 × 3 = 9 separate pipelines, each with its own format, retries and failure handling. Add one new source and you build three more.

With Kafka in the middle, each source writes once and each consumer reads once: 3 + 3 = 6 connections. A new consumer simply starts reading, even from data written last week, without anyone changing the producers.

What makes it different from a queue

In a classic message queue (or a Flume channel), a message disappears once it is delivered. Kafka keeps every event for a configured retention period, 7 days by default, whether or not anyone has read it. Reading only moves the reader's bookmark. That one design choice is what allows replay, many independent readers, and recovery after a consumer crashes.

The vocabulary

Event (record)
One fact that happened, such as "login failed on web01". It has an optional key, a value and a timestamp.
Topic
A named stream of related events, like a table name for data in motion: security-events, payments.
Partition
A topic is split into partitions, and each is an ordered, append-only log. Partitions let a topic spread across brokers and be read in parallel. See it in section 1
Offset
An event's position number within its partition: 0, 1, 2 and so on. It never changes, and it is how readers keep their place.
Producer
Any application that writes events to a topic. The key it chooses decides which partition each event goes to.
Consumer
Any application that reads events, starting from an offset and moving forward.
Consumer group
Consumers sharing one name split a topic's partitions between them, so each event is handled once per group. Different groups each get everything. See it in section 2
Broker
One Kafka server. It stores partitions on its disk and handles reads and writes for them.
Cluster
Several brokers working together, so data survives a server failure and load is shared.
Replica, leader, follower
Each partition is copied to several brokers. The leader copy takes all writes; followers copy it. Fully caught-up copies form the ISR. See it in section 3
Controller
The part of the cluster that manages metadata: it notices dead brokers and chooses new partition leaders. See it in section 4
Retention
How long events are kept, by time (log.retention.hours=168, 7 days) or by size. Old data is deleted whole files at a time, not per read.

How one event travels

  1. The producer hashes the event's key to pick a partition.
  2. It sends the event to the broker that leads that partition.
  3. The leader appends it to the end of the partition log, giving it the next offset.
  4. Follower brokers copy it. With acks=all, the producer is told "stored" only once every in-sync copy has it.
  5. Consumers fetch from their last offset, process the event, and commit their new offset.
  6. When retention expires, the old log file containing it is deleted.
The takeaway
  1. Kafka sits in the middle. Producers and consumers never talk to each other directly, so either side can change or grow without touching the other.
  2. Data is organised as topic, then partition, then offset. A topic is the stream, partitions split it so it can be stored and read in parallel, and an offset is an event's permanent position in its partition.
  3. A cluster is brokers plus controllers. Brokers store copies of the partitions and serve reads and writes. Controllers keep the cluster's own records. Producers and consumers are client applications outside the cluster.
  4. Reading does not delete. Each consumer group keeps its own offset. Events are removed only when retention expires, which is what makes replay and many independent readers possible.

In one sentence: Kafka is a replicated, partitioned log that many producers append to and many consumer groups read independently, and it keeps the data whether or not anyone has read it.

What happened, and why
  1. web01 went to partition 1, at offsets 0, 1 and 2, in the order you sent them. The producer hashes the key and divides by the number of partitions, so the same key always lands in the same partition. Inside a partition events are only ever appended, so web01's events keep their order.
  2. db01 landed in partition 1 too, right after web01. There are far more keys than partitions, so different keys share partitions. That is fine: each key's own events are still in order, they are just interleaved with another key's.
  3. fw01 went to partition 0 and vpn01 to partition 2, each starting again at offset 0. Offsets count separately in each partition. "Offset 2" means nothing on its own: an event is identified by topic, partition and offset together.
  4. The four no-key events were spread across P0, P1 and P2. With no key there is nothing to hash, so the producer spreads events for even load. The price is that there is no ordering between them at all.
  5. Older events never moved or changed number. The log is append-only. New events go to the end with the next offset; nothing is inserted, edited or renumbered.

In one sentence: the key decides the partition, a partition is an append-only log numbered by offsets, and Kafka guarantees order within a partition, which means order per key.

Consumer groups and lag

Consumers in one group split the partitions between them, so each event is processed once per group. A consumer reads by moving its committed offset forward. Lag is how far that bookmark is behind the end of the log. A second application in a different group gets its own bookmarks and reads everything again.

What happened, and why
  1. Lag grew with one consumer. Producers write about 2 events per second, and one consumer handles about 1. Nothing was lost: the extra events waited in the log, and lag counted them. In a real system growing lag means alerts arrive later and later. Step 11's kafka-consumer-groups.sh --describe shows this as the LAG column.
  2. Lag fell with three consumers. The group paused briefly to rebalance, then gave each consumer one partition. Three consumers handle about 3 events per second, faster than the producers write, so they caught up. Kafka scales reading by starting more copies of the same app with the same group name. The producers and the topic did not change.
  3. Two of five consumers sat idle. In one group, each partition is read by exactly one consumer, which is how its order is kept. Three partitions means at most three busy consumers. The partition count you choose at topic creation is the ceiling on parallelism, so plan for future load. Adding partitions later changes which partition each key maps to.
  4. The archive group read everything, then read it again. It kept its own bookmarks, so it received every event the alerting group did without taking any away. Replay set its bookmarks back to 0 and it re-read the whole log, because reading never deleted anything. A Flume channel removes an event once its sink takes it: one destination, no second chance.

In one sentence: a consumer group scales by adding consumers up to the number of partitions, lag shows how far it is behind, and because reading only moves an offset, any number of groups can read and replay the same data independently.

Replication, leaders and acks=all

Each partition is copied to several brokers. One copy is the leader and takes all writes. The others are followers that copy the leader. Followers that are fully caught up form the in-sync replica set (ISR). If a leader's broker dies, an in-sync follower takes over, and no acknowledged event is lost.

What happened
    What happened, and why
    1. Each event went to broker 1, was copied to brokers 2 and 3, and only then was acknowledged. Broker 1 leads partition 0, so it takes the write. With acks=all the producer hears "stored" only after every in-sync copy has the event, so an acknowledged event already exists on three disks.
    2. Broker 1 died and partition 0's leader moved to broker 2. Broker 2 was in the in-sync set, so it had every acknowledged event. Nothing was lost: producers and consumers simply switched to the new leader. Partitions 1 and 2 only lost a follower copy.
    3. The next write still succeeded, with two copies. Two in-sync copies meets min.insync.replicas=2, so acks=all can still be satisfied.
    4. With broker 2 also gone, the write was refused with NotEnoughReplicas. Only one copy was left. Kafka would rather refuse the write, so the producer can retry later, than acknowledge something that one disk failure could erase.
    5. acks=1 accepted the same write. The leader acknowledged as soon as it stored the event. It is faster and keeps working when brokers are down, but that event now lives on a single disk. acks=1 trades safety for availability.
    6. The restarted brokers copied what they missed, then rejoined the in-sync set. A returning broker catches up from the leader before it counts as in sync again. Leadership stays where it moved; real Kafka later hands it back to the original "preferred" broker automatically.

    In one sentence: every partition is copied to several brokers, an in-sync follower takes over when a leader dies, and acks=all with min.insync.replicas=2 guarantees an acknowledged event is on at least two disks.

    Who keeps the cluster's own records?

    Someone must remember which brokers are alive, which topics exist and who leads each partition. That is cluster metadata, and it is managed by one controller. For years Kafka stored it in a separate system, ZooKeeper. With KRaft (Kafka + Raft), Kafka stores it in its own replicated log, and Kafka 4.0 removed ZooKeeper entirely.

    Time is compressed for the classroom. The comparison is the point: with ZooKeeper, recovery grows with the amount of metadata; with KRaft, it does not.

    In your lab (Step 8)

    kafka-storage.sh random-uuid and kafka-storage.sh format create the metadata log on disk, once, like hdfs namenode -format.

    config/kraft/server.properties runs one process as both broker and controller (process.roles=broker,controller). With ZooKeeper you would start zookeeper-server-start.sh first, in its own terminal.

    What happened, and why
    1. At 100,000 partitions, ZooKeeper mode took several times longer than KRaft. Nearly all of that time was step 3. The new ZooKeeper-era controller started with nothing and had to read every partition's record back from ZooKeeper before it could make a single decision.
    2. A third of the partitions had no leader on the ZooKeeper side; KRaft showed 0. In ZooKeeper mode the controller is also an ordinary broker, so its partitions lost their leader too, and nobody could elect new ones until the metadata was loaded. KRaft controllers are separate from the brokers, so brokers kept serving data while the controllers sorted themselves out.
    3. At 1,000 partitions the gap shrank to about a second. On small clusters there is little metadata to reload, so the ZooKeeper cost is barely visible, which is why the design lasted for years.
    4. At 200,000 the ZooKeeper time grew again, and the KRaft time did not change. ZooKeeper recovery grows with the amount of metadata. KRaft standbys have been replicating the __cluster_metadata log with Raft all along, so a takeover is just a quick vote, whatever the size.
    5. Two systems against one. ZooKeeper is a separate product with its own servers, security and upgrades. KRaft removes it: the controllers are Kafka. In your lab one process plays both broker and controller, which is fine for learning, but production clusters run three dedicated controllers.

    In one sentence: KRaft moved Kafka's metadata from ZooKeeper into a Raft-replicated log inside Kafka, so standby controllers are always ready, failover no longer grows with cluster size, and there is one system to run instead of two.

    Apache Flume: collecting logs and moving them in

    Kafka stores and serves events, but something has to collect them from the servers that write log files. Apache Flume is a collector from the Hadoop ecosystem built for exactly that: you describe a pipeline in a config file, start an agent, and it moves log lines into HDFS, Kafka or another destination, with no code.

    An agent is three parts in one JVM process

    Every Flume agent has a source that reads input, a channel that buffers events, and a sink that writes them out. Data moves in transactions: the source commits a batch into the channel, and the sink removes events from the channel only after it has written them. That handshake is what makes Flume reliable, as long as the channel itself survives.

    Sources
    exec (runs tail -F), TAILDIR (tails files and remembers its position), spooldir, syslog, netcat, kafka
    Channels
    memory (fast, lost on crash), file (write-ahead log on disk), kafka (Kafka holds the buffer)
    Sinks
    hdfs, kafka, hbase, logger, avro (to chain agents together)

    The same parts, in your lab's config

    Every line is agent.component.name.setting. The agent name must match -n a1 when you start it, and a typo is silently ignored. Note that the source says channels (it can feed several) while the sink says channel (it reads exactly one).

    Changing the source or channel resets the run. The sink is deliberately slower than the source, as HDFS writes are, so a backlog builds up in the channel.

    The HDFS sink and the small-files trap

    The HDFS sink starts a new file whenever any of three limits is hit: hdfs.rollCount (default 10 events), hdfs.rollSize (default 1 KB) and hdfs.rollInterval (default 30 seconds). With the defaults, a busy agent creates a file every few events. The NameNode keeps every file and block in memory, roughly 150 bytes each, so millions of tiny files slow the whole cluster down.

    The lab sets rollSize to 128 MB (one block), rollCount = 0 (off) and rollInterval = 60 as a backstop so a quiet source still closes its file.

    What happened, and why
    1. memory + exec lost most of the lines. Three groups disappeared at once. Events waiting in the channel lived in the JVM's RAM, which died with the process. Lines the source had read but not yet handed to the channel were also in RAM. And on restart, tail -F jumped to the end of the file, so every line it had not read was skipped. Only lines already in HDFS survived.
    2. file + exec delivered the channel's backlog after the restart, but still lost lines. The channel showed "safe on disk": its write-ahead log was replayed on restart, just like the replay in your flume.log. The source, though, still forgot its place. A few duplicates can appear when the sink had written a batch but crashed before removing it from the channel, so it was sent again.
    3. file + TAILDIR lost nothing. TAILDIR saves its read position to disk, so after the restart it carried on from where it had committed. With both the buffer and the position on disk, every line arrives at least once. Occasional duplicates are the price: at-least-once delivery.
    4. Lines written while the agent was down: exec skipped them all, TAILDIR collected them. This is the realistic case. Servers keep logging during an outage, and only a source that remembers its position can go back for those lines.
    5. Defaults made 10,000 files of about 950 bytes; the lab settings made 1. With rollCount=10 the sink closes a file every 10 events. Every file and block costs NameNode memory, and every small file becomes its own task when MapReduce or Spark reads the data. Rolling on size near one block avoids both problems.

    In one sentence: a Flume pipeline is only as durable as its weakest in-memory part: a file channel protects the buffer, TAILDIR protects the read position, and the cost of both is possible duplicates.
